# Darling 聊天软件：需求与设计要点

记录日期：2026-10-15。当前阶段：需求分析与架构确定，尚未开始应用实现。具体选型和模块责任以 [架构基线 v1](architecture.md) 为准。

本文区分已确认需求、建议方案和待实测事项；技术选型与性能数字均不代表已实现或已验证。

## 1. 已确认需求

- Windows 桌面客户端，使用 Electron 构建页面。
- 首期提供文字聊天和实时语音通话；后续扩展截图、文件传输、远程桌面。
- 音质优先级极高：充分利用现有音频设备的有效收音能力，优秀回声消除和降噪，同时控制电脑资源消耗。
- 亚克力背景、圆角窗口、现代霓虹配色。
- 远程 Debian 服务器，具备公网 IP，无域名。
- 当前不将网络安全加固作为项目设计重点。
- 客户端读取配置文件中的用户名、密码，启动后自动登录，不提供登录页面。
- 当前仅两个用户：`dva`、`mercy`。
- 已确认资源存在：`resource/dva.png`、`resource/dva_avatar.png`、`resource/mercy.png`、`resource/mercy_avatar.png`。按文件名分别映射为用户图标与头像，实际尺寸及裁切方式在界面阶段检查。

## 2. 产品边界与默认假设

首期按两个用户的一对一会话设计，不引入群组、好友申请、注册、账户管理后台。自动登录成功后直接进入双方会话。文字聊天与通话可以同时使用。

语音暂按“发起—响铃—接听/拒绝—通话—挂断”交互设计；自动登录不等于自动打开麦克风，也不等于自动接听。若实际需要常驻语音房，可替换通话交互而保留媒体层。

建议首期包括消息持久化、离线消息补拉、发送状态、在线状态、掉线重连、输入/输出设备选择、静音、扬声器音量和通话状态。已读回执、多端同时在线、全文搜索暂不作为首期硬要求。

## 3. 音频目标与取舍

“最好收音”指在当前设备能力范围内保留人声音色、细节与动态，不简单等同于最高采样率、最大增益或最强降噪。削波、硬件底噪、扬声器失真和设备固件处理无法通过后期算法完全恢复。

回声消除、强降噪、音色自然度与计算量需要联合调优。不能在未知麦克风、声学环境及 CPU 的条件下承诺一种算法在所有场景中都最好；最终以双方实际设备的试听和测量确定默认参数。

### 3.1 推荐方向：Electron UI + 独立原生媒体引擎

- Electron 负责页面、窗口、配置、业务状态；原生进程负责音频设备、实时处理、编码、传输和播放。
- 原生媒体引擎优先评估 C++、WASAPI、libwebrtc。将采集和播放一起交给媒体引擎，保证回声参考与时钟可控。
- Electron 与媒体进程只交换控制消息、状态和低频统计；不通过页面 IPC 高频搬运 PCM，不把实时音频回调放入 JS 主线程。
- 原生引擎增加编译、打包和版本维护成本，但更适合精细控制设备与处理链。先做技术验证，再锁定实现。
- Chromium 自带 WebRTC 作为对照基线：开发和维护较简单，但网页媒体约束不能视为已成功启用设备 RAW、精确位深或指定内部 AEC 参数。必须检查实际设置与录音效果。
- 不默认采用“原生处理后再送回浏览器编码”的混合链路，避免额外缓冲、复制及重复处理。

### 3.2 采集与设备策略

- 优先使用 WASAPI 共享模式，避免独占麦克风/输出设备影响游戏与其他应用。
- 检查 RAW 支持及实际生效的设备效果。RAW 可减少系统自适应处理，但可能失去厂商有效的阵列处理；与设备默认模式进行 A/B 对比后选择。[1]
- 优先保留设备有效位深，内部采用浮点处理；通信处理基线为 48 kHz、单声道人声。设备格式不同时只在必要边界重采样，避免反复转换。
- 不为人声通信默认使用 96/192 kHz，不把双声道当作音质保证。阵列设备的多通道处理应在合理阶段完成，而非盲目取其中一路。
- 系统、驱动、浏览器、应用各层的 AEC、降噪和自动增益不得无意识叠加。需要记录哪一层拥有处理权。
- 保存稳定设备标识，支持热插拔、默认设备变化、采集失败提示与显式回退。切换设备后重建必要缓冲和回声状态。
- 蓝牙设备的双向通话能力因硬件和驱动而异，单独实测；不能承诺软件突破设备链路上限。

### 3.3 候选处理链

```text
麦克风 → 格式整理/必要重采样 → AEC → 一套主要降噪器
       → 温和电平管理/限幅 → Opus 编码 → WebRTC 传输

网络 → 抖动缓冲/丢包处理 → 解码 → 应用播放混音/音量 → 输出设备
                                         └→ AEC 播放参考
```

- AEC 首选评估 WebRTC AEC3；输入必须包括时间对齐的播放参考，同时处理输出延迟与设备时钟漂移。WebRTC APM 提供回声消除、降噪和增益处理基础能力。[2]
- 参考应尽可能对应实际输出音频，并包含应用内混音与音量变化。基础范围覆盖本应用播放声音；游戏、音乐等其他应用外放声的消除需要另行验证系统回环参考方案，不能直接宣称已覆盖。
- 重点测试双方同时说话（双讲）：不能通过压低或切断近端人声来制造“没有回声”的假象。
- 降噪比较 WebRTC NS 与 RNNoise，选一套主要方案；RNNoise 是轻量神经网络降噪候选，不默认叠加强 NS。[3]
- 默认偏向自然音色，提供自然/均衡/强降噪档位。强档须清楚评估轻声、尾音、气声、键盘声和人声干扰的影响。
- 自动增益保持保守，避免底噪抽吸和突然改变音量；硬削波应通过输入电平调整处理。
- 不用硬噪声门代替降噪。VAD 主要用于说话指示及统计，不默认切断低音量语音。

### 3.4 编码与网络

- Opus 作为首选，初始实验参数为 48 kHz 单声道、64–96 kbit/s、20 ms 帧；这些是待试听的起点，不是最终质量承诺。[4]
- 对比 10 ms 与 20 ms 帧的延迟、CPU、包开销；编码复杂度按目标机器测量，不一律拉满。
- 根据丢包和网络状态调整码率、FEC 与抖动缓冲；DTX 单独比较，优先避免轻声和句首被截断。
- 语音使用 WebRTC 媒体传输；文字使用可靠业务通道。不要把实时语音排入普通 WebSocket 消息队列。
- 双人通话优先 P2P，Debian 提供 STUN/TURN 兜底；公网服务器不代表两个客户端可以直接互通。[5]
- TURN 中继不解码或重新编码音频。首期不需要多人 SFU 或服务器混音。

## 4. 系统划分与服务端

| 部分 | 建议职责 |
| --- | --- |
| Electron 页面 | 会话、消息、通话控件、设备设置、视觉效果 |
| Electron 主进程 | 本地配置、自动登录协调、窗口、托盘、原生进程生命周期 |
| 原生媒体进程 | WASAPI、AEC/NS、Opus、WebRTC、音频统计 |
| Debian 业务服务 | 两个账号校验、在线状态、消息存储、通话信令、重连同步 |
| Debian TURN 服务 | NAT 穿透失败时中继媒体 |

建议业务服务使用 Node.js/TypeScript 与 WebSocket，SQLite 保存用户及消息；双用户规模不需要 Redis、微服务或大型数据库。Debian 使用 systemd 管理进程与日志，coturn 作为 TURN 候选。

客户端使用本地打包页面，业务地址配置为公网 IP 与端口；不依赖远程 HTTP 页面来申请麦克风。无域名不妨碍 IP 连接，但部署仍需明确监听端口、TURN relay UDP 范围及网络放通条件。

按需求不扩展安全加固工程。WebRTC 自带的 DTLS-SRTP 等协议机制仍正常保留；无域名、暂不加固不等于需要移除协议必需功能。

文字消息包含协议版本、消息 ID、会话 ID、发送者、类型、内容、服务端时间和会话序号。客户端生成唯一 ID，服务端确认并去重；断线后按服务端序号补拉，避免重发造成重复消息。

## 5. 配置登录与失败处理

建议客户端配置放在应用 userData 目录的 `config.json`，配置路径稳定且不随安装包更新覆盖。下列仅为结构示例，不创建真实凭证：

```json
{
  "schemaVersion": 1,
  "server": { "url": "ws://<公网IP>:<业务端口>" },
  "auth": { "username": "dva", "password": "<配置密码>" },
  "audio": {
    "inputDeviceId": "default",
    "outputDeviceId": "default",
    "profile": "balanced"
  }
}
```

用户名仅允许 `dva`、`mercy`，由服务端验证凭证并返回身份；不能只在客户端检查用户名。服务端账号配置与客户端文件分开管理。

启动流程：读取/校验配置 → 展示主窗口连接状态 → 自动鉴权 → 加载历史与在线状态 → 可聊天。密码不回传页面、不写日志。

没有登录页面，但必须有错误呈现：配置缺失/格式错误显示配置路径和可读原因；凭证错误停止自动重试，提示修改配置后重试；网络不可达使用带退避的自动重连并提供重试入口。不显示用户名密码输入框。

先按每个用户一个活跃客户端设计，多设备重复登录的处理策略在实现前固定。连接状态、鉴权状态和通话状态分开管理，避免网络重连误触发新通话。

## 6. 界面与视觉

- 建议深蓝黑基底、半透明亚克力面板，以霓虹粉和青色作交互强调；dva 可偏粉，mercy 可用暖金作为身份点缀。身份色为建议，待结合实际资源视觉确认。
- 布局以单一双人会话为中心：紧凑身份/在线栏、消息区域、输入区域、稳定可见的通话控制。通话时可展示双头像、计时、静音与连接质量。
- 霓虹光主要用于选中态、呼叫、说话状态，避免全文发光及持续大面积动画；正文使用高对比中性色。
- 优先系统绘制 Acrylic 与窗口圆角，保留拖动、边缘缩放、最大化还原与系统阴影。CSS 圆角不能替代原生窗口圆角。
- Electron 的圆角支持取决于系统版本：文档标注 Windows 11 Build 22000 起可用；背景材质还需按最终 Electron/Windows 版本验证。[6]
- 建议以 Windows 11 为完整视觉目标；Windows 10 或关闭透明效果时回退为深色不透明背景。若 Windows 10 也要求完整亚克力与圆角，需要单独评估原生兼容实现。
- 窗口最小化/后台暂停无意义动画，声级指示限频更新。亚克力效果与 GPU/功耗一起验收。

## 7. 后续扩展预留

采用能力模块边界，不提前构建复杂插件市场。消息类型预留 `text`、`image`、`file`、`system`，旧客户端对未知类型给出占位提示。

- 截图：本地截图、区域选择与预览，再接入图片附件消息。
- 文件：元数据与消息分离，文件内容独立传输，支持进度、取消及后续断点续传。大文件不能阻塞文字或通话信令。
- 远程桌面：屏幕采集、视频编码、输入控制与会话状态独立模块化；复用信令和媒体基础设施。屏幕共享与可控制桌面是两种能力，需要分别定义。
- 传输调度优先语音，其次控制与文字，最后批量文件；新增功能时验证音频不受带宽或 CPU 争用影响。

## 8. 验证与暂定预算

以下仅作为原型测量目标，最终验收必须绑定双方 CPU、Windows 版本、麦克风、输出设备与网络条件。

| 项目 | 初始目标/验收方法 |
| --- | --- |
| 音色 | 同一设备原始录音与处理后录音盲听，保留轻声、尾音、气声与自然动态 |
| 回声 | 耳机、外放、大小音量、双讲、切换设备均测试；稳定外放场景无明显可感知回声 |
| 降噪 | 风扇、键盘、空调、突发声分别评估，背景人声单列；记录改善与人声损伤 |
| 端到端延迟 | 良好网络下争取 150 ms 以内；区分采集/DSP/编码/网络/播放延迟 |
| DSP 时间 | 若采用 10 ms 处理块，争取处理耗时 P95 ≤ 2 ms，并监测 P99 与超时 |
| CPU | 媒体进程平均争取低于单逻辑核心 10%，明确统计口径；UI/GPU 另测 |
| 内存 | 客户端所有进程工作集初始争取 ≤ 350 MB，媒体进程单独记录 |
| 稳定性 | 连续通话至少 2 小时，检查音频断续、漂移、内存增长和重连 |
| 网络 | 记录真实 RTT/抖动，模拟 1%、3%、5% 丢包及短时断网，观察可懂度与恢复 |
| 并发负载 | 游戏/文件传输/窗口缩放与后台运行时检查语音连续性和 CPU 峰值 |

保存原型的实际协商采样率、码率、音频处理开关及统计日志。原始/处理后音频只在明确启动的诊断测试中记录，不默认录制私人通话。

## 9. 实施顺序与尚未确定事项

1. 音频原型：同一设备比较 Chromium WebRTC 基线与原生 WASAPI + AEC3 + 候选降噪链，验证原始采集、双讲、延迟和 CPU。
2. 双用户通信闭环：自动登录、文字持久化、通话信令、P2P/TURN、断线恢复。
3. Electron 正式界面：头像资源、亚克力、圆角、霓虹主题、设备设置与错误状态。
4. 实机验收与安装包：固定依赖版本、Debian 部署说明、性能数据和音质参数。
5. 按需扩展截图、文件和远程桌面。

待后续补充：双方 Windows 版本、CPU、音频设备型号、耳机/外放使用比例、服务器 IP/端口及 Debian 版本、凭证、是否需要自动加入常驻语音、多设备策略、消息历史保留时间。这些不阻塞本次设计记录，但影响最终实现及验收。
