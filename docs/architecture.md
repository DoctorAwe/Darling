# Darling 架构基线 v1

日期：2026-10-15。状态：本轮确定的实现架构；尚未实现或通过性能验收。

需求来源：[设计要点](design-notes.md)。本文将其中的技术候选收敛为实现基线；音频参数保留实测调优空间，模块边界保持稳定。

## 1. 架构决策

采用 **Electron 桌面应用 + C++ 独立媒体进程 + Debian 单体业务服务 + coturn**。

| 层 | 确定选型 | 责任 |
| --- | --- | --- |
| 页面 | React + TypeScript + Vite | 会话、消息、设备设置、通话交互、霓虹主题 |
| 桌面宿主 | Electron 主进程 + preload | 配置、业务连接、窗口、媒体进程管理、本地状态 |
| 实时媒体 | C++ 独立可执行程序 + libwebrtc | WASAPI 采集/播放、音频处理、Opus、ICE/WebRTC |
| 业务服务 | Node.js + TypeScript + Fastify + WebSocket | 自动登录、消息、在线状态、通话协调 |
| 存储 | 服务端 SQLite，启用 WAL | 消息、会话序号、迁移版本 |
| 穿透/中继 | coturn | STUN/TURN，UDP 优先，TCP 中继作为备选 |
| 部署 | Debian + systemd | 业务与 TURN 两个服务的生命周期 |
| 工程 | pnpm workspace；原生代码独立构建 | 共享业务协议、桌面/服务端构建与发布 |

首期 Windows x64 为实现目标。Windows 11 为完整视觉体验基线；旧系统材质回退。服务器不运行音频降噪、混音或转码。暂不引入 SFU、Redis、微服务及通用插件系统。

## 2. 进程与数据流

```mermaid
flowchart LR
  subgraph Windows 客户端（双方相同）
    UI[React 页面] <-->|有限类型 IPC| MAIN[Electron 主进程]
    MAIN <-->|版本化 JSON / stdio| MEDIA[C++ 媒体进程]
    MEDIA <--> AUDIO[WASAPI 设备]
  end
  MAIN <-->|WebSocket：身份/消息/信令| API[Debian 业务服务]
  API <--> DB[(SQLite)]
  MEDIA <-->|WebRTC 媒体直连| PEER[对端媒体进程]
  MEDIA <-->|直连失败时中继| TURN[coturn]
  TURN <--> PEER
```

页面不持有服务端密码，不直接连业务服务，不直接操作声卡。主进程是客户端业务状态的唯一权威，页面订阅快照和增量事件。媒体进程是设备与媒体状态的唯一权威，主进程将其状态转换为 UI 可用的信息。

原生进程采用隐藏子进程启动，stdin/stdout 用长度受限的逐行 JSON 通信；stdout 仅供协议，stderr 用于诊断。消息包含 `protocolVersion`、`requestId`、`type`、`payload`，响应关联 requestId；异步事件拥有独立 type。启动必须先完成版本/能力握手，不兼容时停止启动并显示原因。

IPC 只传控制与低频统计，不传 PCM 或编码媒体。声级事件最多 20 Hz，详细统计默认 1 Hz；队列有界，过期统计可丢弃。媒体进程异常后结束当前通话并释放状态，可重启待命，不自动恢复麦克风采集。退出时先正常停止再按超时终止子进程。

## 3. 原生媒体引擎的内部边界

媒体进程内部采用 `DeviceBackend`、`AudioPipeline`、`RtcSession`、`Diagnostics` 四个模块；外部仅暴露 `MediaEngine` 控制接口。

- `DeviceBackend`：基于 WASAPI 实现 libwebrtc 自定义 AudioDeviceModule（ADM），负责共享模式、RAW 能力尝试、设备枚举、热插拔、时间戳和输出延迟。RAW 不可用时报告实际回退，不伪报成功。
- `AudioPipeline`：通过 libwebrtc APM 处理一次 AEC3；降噪基线选 RNNoise，关闭重复 WebRTC NS。通过所锁定版本的 APM 自定义处理钩子在 AEC 后接入；构建原型必须核实钩子的执行顺序和采样格式。如果不符合要求，在同一原生模块中做最小适配并记录补丁，不额外串联第二套完整 APM。
- `RtcSession`：原生 PeerConnection、SDP/ICE、Opus、拥塞反馈、抖动缓冲与播放；不将处理结果交回 Chromium 二次编码。
- `Diagnostics`：报告实际采样格式、活动处理器、丢包、RTT、处理耗时和欠载；录音仅由显式诊断操作启用。

音频采集/播放使用专用实时线程和预分配有界缓冲，控制命令投递至控制线程。实时回调不等待 JS、磁盘、网络日志或模型加载，不在回调中频繁分配内存。

处理链确定为：设备采集 → 必要格式转换 → AEC3 → RNNoise → 温和电平管理/限幅 → Opus。APM 内部工作格式按锁定版本适配，不宣称所有内部环节都是浮点无损。发送基线为 48 kHz 单声道、80 kbit/s、20 ms 帧，DTX 初始关闭，FEC 根据网络情况启用；参数可调，最终以测试为准。

接收音频解码后，经应用混音/音量进入输出，同时给 AEC 提供一致的播放参考；应用通话中提示音也进入这一播放路径。输出设备变化需要更新参考、延迟和 AEC 状态。其他软件外放声音的消除不属于首期已保证能力。

降噪器保留实现接口，WebRTC NS 作为可测量的替代实现；同一时刻只启用一个主要降噪器。RNNoise 是否达到双方设备所需的抑噪与保真度是验收问题，替换它不改变 IPC、传输或业务架构。

libwebrtc 固定到具体 commit，RNNoise 同样锁定版本；不跟随浮动主分支。libwebrtc 使用其 GN/Ninja 工具链，媒体程序以原生构建目标集成；脚本输出可打包的 exe、运行依赖、许可证和版本清单。依赖编译体积和时长属于开发成本，不等同运行时占用。

## 4. 业务协议与持久化

业务 WebSocket 由 Electron 主进程唯一持有。协议使用共享 TypeScript schema 做运行时验证，统一信封包含 `version`、`type`、`requestId`、`payload`；服务端推送包含必要的实体 ID/序号。

主要消息族：`auth.*`、`presence.*`、`message.*`、`call.*`、`rtc.*`。`rtc.*` 只转发 SDP 与 ICE，不转发音频。所有通话信令绑定 `callId` 和协商代数，丢弃旧通话、旧 ICE restart 的迟到事件。

SQLite 首期表：`conversations`、`messages`、`schema_migrations`。用户 dva/mercy 及凭证来自服务端独立配置，头像来自客户端资源映射。固定一个双人会话，但数据结构使用会话 ID，避免未来附件扩展修改基础协议。

消息记录至少包括：服务端 ID、客户端生成 ID、会话 ID、发送者、类型、内容、服务端时间、会话递增序号。对“发送者 + 客户端生成 ID”加唯一约束；序号分配和插入放在同一事务中。只有落盘提交后才返回确认并广播；收到重复发送时返回原记录。

客户端先显示待发送消息，确认后替换为服务端记录。同步使用会话序号分页补拉，按 ID 合并，最后连续序号作为游标，允许补拉与在线推送交错。首期界面区分“发送中/已存储/失败”，不把服务器已存储误称对方已读。

本地轻量状态保存在 userData：配置、最后同步游标、有限待发队列。待发队列采用原子文件替换，限制大小；同一逻辑消息重试使用原客户端 ID。历史以服务器为准，客户端重启后重新补拉，首期不引入第二套本地消息数据库。

## 5. 自动登录、会话与恢复

读取 userData/config.json → 校验 → 连接 IP:端口 → 发送凭证 → 服务端确认身份 → 同步消息/在线状态。页面从开始就显示主界面及连接状态，不出现登录表单。

缺配置、错误凭证进入明确错误状态，提供配置路径与重新加载入口；网络故障退避重试并带抖动。凭证错误不循环重试。服务端以已鉴权连接身份作为消息发送者，不信任消息体传入的用户名。

每个用户一个活跃会话：新连接登录成功替换旧连接，旧连接收到 `session.replaced` 后停止自动重连，防止两个实例互相挤占。重连的旧连接关闭事件不能把新的会话标记离线。

通话由服务端维护有限状态：`idle → ringing → connecting → active → ended`；客户端另有 `reconnecting/failed` 展示。服务端分配 callId，原子处理邀请，双方同时呼叫时返回已存在的同一通话，避免建立两路媒体。

邀请超时默认 30 秒；拒绝、忙线、取消和挂断有明确原因码。只有接听后进入协商和麦克风采集。邀请者生成 offer，接听者生成 answer；后续协商由服务端明确指定发起方，早到 ICE 按 callId/代数有界暂存。

信令短断时已有媒体可在 15 秒恢复窗口内继续；重连后从服务端获取通话快照并核对双方会话。恢复失败则结束通话并关闭采集。媒体连接失败可在恢复窗口内尝试 ICE restart，超过窗口结束；不无限保留“正在通话”假状态。

## 6. Debian 部署边界

业务服务和 coturn 分进程部署，SQLite 数据和附件预留目录位于持久化目录。业务端口及 TURN 端口/relay 范围在配置中指定，实际部署时统一生成说明。无域名阶段业务可采用 `ws://公网IP:端口`，页面是本地资源。

业务服务登录响应下发 ICE server 配置；TURN 使用服务端生成的有期限凭据，并在新建或重新协商连接前检查有效期。不是开放匿名中继。使用 WebRTC 标准媒体协议，不为省略安全工程自行替换传输栈。

消息写入与通话状态在单业务进程内协调；不设计多副本。服务器重启后清空在线/通话内存状态，客户端重新登录和同步；旧通话结束，消息继续保留。SQLite 设置迁移、保留策略配置和可恢复备份流程，默认不自动清理历史。

## 7. UI 与扩展

React 页面使用 CSS 变量定义颜色、透明度、圆角和动态效果，轻量状态订阅即可，不依赖重型组件库。Windows 原生 Acrylic/圆角由 Electron 主进程负责；最大化、恢复、缩放及不支持系统的回退统一封装在窗口模块。

截图、文件、远程桌面各有独立能力接口：截图输出附件；文件上传下载走独立 HTTP 流及任务队列；远程桌面后续新增视频轨道与控制通道。控制会话不复用聊天消息队列，需有显式开始/结束状态。语音始终优先，文件并发/速率与视频码率可限额。

## 8. 目录与落地顺序

```text
apps/desktop/           Electron main、preload、React renderer
apps/server/            鉴权、消息、在线状态、通话协调、数据库
packages/protocol/      业务与桌面 IPC schema、错误码
native/media-engine/    WASAPI、APM/RNNoise、PeerConnection、stdio 协议
native/protocol/        原生 IPC 定义和跨语言一致性样例
scripts/                原生依赖构建、打包与开发启动
deploy/debian/          systemd、coturn 示例和部署说明
resource/               现有用户图标和头像
docs/                   需求、架构、性能测量记录
```

按纵向可验证交付推进：

1. 建立 workspace、协议定义、配置加载、服务端鉴权与桌面主窗口，完成双用户自动登录。
2. 实现 SQLite 消息、去重、补拉、在线状态和断线恢复，形成可用文字聊天。
3. 构建锁定的 libwebrtc/RNNoise 和媒体子进程，先验证握手、设备枚举、采集/播放及处理链；同时验证 AEC/RNNoise 插入顺序。这一步通过后才能宣称原生音频基础可用。
4. 接入通话状态机、SDP/ICE 与 TURN，完成双端真实通话，再做音质/性能调优。
5. 完成亚克力/霓虹交互、打包、Debian 部署和双方实机验收。

优先验证的风险为：自定义 ADM/APM 接入正确性、播放参考延迟、RAW 实际支持、RNNoise 人声损伤、libwebrtc 构建维护成本。风险出现时在媒体引擎内部调整实现；不得默默改用浏览器采集并声称实现了原生音频链。

架构完成的标志是边界与协议责任明确；音质完成的标志是实机测试通过。现有音质和性能目标继续见 design-notes.md，尚无测量结果。
