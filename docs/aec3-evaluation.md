# AEC3 隔离验证 · 2026-10-16

## 当前结论

**最新增益诊断：** `--diagnose-trace` 显示双讲窗口 1750 块全部被判为近端且线性估计可用，无饱和；平均幅度增益仅 0.1404。近端状态的 mask_hf 候选 {3,4,0.3}（`--diagnose-nearend-mask`）将相关性提升至 0.9016、增益损失降至 1.886 dB，稳态回声衰减未变化，但 SNR 7.2766 dB 仍低于 8 dB 门槛，**候选尚未通过，不启用**。统计只覆盖 16 kHz 低频带内部频点，不能称为 48 kHz 全频性能。仍需独立验证集避免对当前种子过拟合。

**2026-10-17 定位补充：** 新增三组离线对照。降低单一近端 SNR 检测门槛无效；给近端噪声加入起伏/停顿也未通过。导出抑制前 linear AEC 的 16 kHz 低频带后，近端相关性 0.995679、增益 −0.007689 dB，而完整输出仍有约 12.82 dB 损失，证据指向线性滤波后的抑制阶段。此结论仅覆盖当前合成场景及低频带，不等于已确认具体根因或已修复。

重现命令：先编译 `aec3-evaluation` 目标，然后对生成的 exe 分别传入 `--diagnose-nearend-snr`、`--diagnose-modulated-nearend`、`--diagnose-linear-output`。诊断仍返回完整输出质量门槛的失败码；默认 CTest 不选取这些 profile。实时引擎始终使用默认配置，诊断导出不会替换处理后的 PCM。

**2026-10-17 质量门槛更新：扩展双讲测试失败。** `tests/aec3_scenarios.cpp` 新增独立近端/远端合成信号、延迟及增益突变，以及 120 秒加速流。双讲相关性 0.522、近端增益 −12.82 dB、基线 SNR 1.34 dB，均未达门槛；简单延迟对齐排查无改善。回声路径变化后稳态衰减 62.17 dB；加速流输出有限。CTest 返回失败是当前真实验收状态，不应降低门槛或据此前“通路通过”开启默认 AEC。没有实际语音主观测试，根因尚待确认。

**最新进度补充：** `native:aec3-evaluate` 现在还构建独立 `darling-media-aec3.exe`，不安装覆盖默认客户端。`pnpm native:aec3-smoke` 是显式硬件测试，会开启默认麦克风并播放两轮各 1 秒低幅度提示音。两轮真实通路均通过，模式为 aec3-experimental，每轮消费 100 个参考块；这是通路与会话重置验证，不是声学质量验收。以下离线测试历史仍有效，但“尚未链接到 darling-media”仅指默认引擎；实验可执行文件已链接适配器。

真实 AEC3 算法已通过 Windows/MSVC x64 的离线合成测试。**尚未链接到 darling-media，客户端 AEC 能力仍为 false，采集仍是 bypass。** 本次不开麦克风、不播放、不记录用户音频。

## 重现

运行 `pnpm native:aec3-evaluate`，或 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-native.ps1 -EvaluateAec3`。

脚本在 `native/media-engine/build/aec3-evaluation` 独立配置、构建和执行 CTest；首次需要网络。不会安装或覆盖客户端引擎。正常 `native:build` 显式关闭实验目标。

依赖来自 [Enaium/webrtc-aec3](https://github.com/Enaium/webrtc-aec3)，不是官方 WebRTC 发布包：

- 固定提交：`2cec2f52e26646f93bd2d5498bbabf59cba18da9`。
- 下载包 SHA-256：`3bc3423e71b7280cf96d87b2e429444ed3fee364b94648ce9875ee95b8f485f8`。
- BSD-3-Clause；许可证复制到测试 exe 同目录。生产分发前还需检查完整第三方许可证、PATENTS 和原始 WebRTC revision 的对应关系。
- 不执行该项目的构建脚本。Darling 自有 CMake 仅编译源码；MSVC 向量下标兼容修正只作用于构建目录中的副本，补充 array 头文件与数学常量定义。
- 提取版带有简化的 Environment/Abseil 兼容层；`cpu_info::Supports` 恒为 false，因此 AEC3 优化选择为 scalar，不能把本测试称为官方完整 APM 验证，也没有证明 AVX2 分支正确。

## 测试方法与一次本机结果

48 kHz 单声道，每帧 480 样本。normalized float 转 FloatS16 后进入 AudioBuffer，48 kHz 分成三个频带，处理后重组并还原尺度。每个场景重新建立处理器。

- 固定 xorshift 种子的低通随机远端信号，主回声延迟 100 ms、增益 0.6，另有 15 ms 后的反射、增益 0.15。20 秒数据，后 10 秒计算输入/输出能量比；要求衰减 ≥15 dB。本次为 **66.6233 dB**。
- 无远端播放，仅近端合成信号；后 10 秒能量衰减绝对值要求 <3 dB，防止以静音冒充消回声。本次为 **0.145112 dB**。能量检查不是语音保真度验证。
- 全部输出检查有限值、幅度范围。每帧耗时涵盖输入准备、分频、AEC3、重组和输出检查；回声场景 P50 **162 μs**、P95 **200.8 μs**；近端场景 P50 **112.8 μs**、P95 **149.1 μs**。耗时随运行负载变化，不作为跨机器硬门槛。

没有测试真实房间、扬声器失真、双讲、风噪、设备时钟漂移、参考队列抖动、长时间稳定性或端到端通话。以上数字不是用户实际通话效果或整机 CPU 占用承诺。

固定哈希下载包的全新目录构建和 CTest 已通过；复测衰减分别保持 66.6233 / 0.145112 dB，回声场景 P95 为 205.8 μs。正常原生构建与 2 项 CTest、TypeScript 类型检查也通过。未重新运行 UI 或设备诊断。

## 接入前的下一步

适配层更新：离线测试已改用 `src/aec3_processor.{h,cpp}` 的统一 AudioProcessor 接口，不再在测试中重复实现 WebRTC 调用。reset 仅允许在音频线程停止时调用；测试验证使用后的实例重置与新实例连续 100 帧输出一致，且保留所有输入帧元数据。三类场景结果不变；本次回声 P95 206.5 μs，耳机 P95 204.5 μs。适配器尚未绑定 WASAPI 队列，构造/重置分配与算法内部实时分配审计不能混为一谈。

2026-10-16 追加：新增有远端播放、独立近端信号、零声学回声的耳机场景，以及近端信号延迟补偿相关性门槛（>0.9）。耳机与无远端场景均为衰减 0.14492 dB、相关系数 0.959874；耳机场景 P95 206.2 μs。与前文相比，近端信号改为独立的第二段随机序列。详见 `docs/audio-device-policy.md`；这仍不是真实双讲验收。

1. 决定是否保留此提取版，或换为可追溯的完整官方 APM 构建；补齐来源、许可证和 SIMD 检查。
2. 实现可测试的 AudioProcessor 适配器，处理生命周期/设备切换/丢帧重置，不在音频回调中创建算法对象。
3. 正确处理播放提交时间、padding 和采集时间；不能将提交 QPC 当成实际扬声器时间，也不能任意把全部未来参考帧灌入算法。
4. 添加多种延迟、回声路径突变、双讲保真度和输入静音测试，再执行用户明确触发的真实设备验证。
5. 验证后才开启 AEC 能力；RNNoise、RTC 仍为后续任务。
